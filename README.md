# PQ-Proof

Give PQ-Proof a repository URL. An agent inventories the repo's cryptography, patches its TLS key exchange to hybrid ML-KEM (`X25519MLKEM768`), and proves the change inside isolated microVMs on Vultr: a real handshake, the repo's own tests, and a classical client that still connects. You get a hashed receipt and a diff.

**Live demo: https://149-28-14-122.sslip.io/** replays recorded runs. In the newest, `e2e-glm-7`, `glm-5.3` on Vultr Serverless Inference wrote the plan and the patch, and microVMs on a Vultr VX1 host built and proved it (78.2 s, $0.0159 in tokens, verdict PASS). `e2e-injection-scripted-1` shows the TLS-weakening check refusing a patch that follows the fixture README's prompt injection (a scripted stand-in, no model call). The page re-checks each run's hashed receipt on every request. Nothing on the demo site starts a run or calls a model.

Built for the Vultr Agent Rush hackathon (November 2026), challenge 1, Blast Radius Zero.

## Architecture

The control plane is one Python (3.12+) process that sticks to the standard library where it can. It drives [Microsandbox](https://github.com/superradcompany/microsandbox) through the `msb` CLI from the official installer, so every action that touches a sandbox is a plain command line that is logged and can go into the receipt. Model calls go to Vultr Serverless Inference's OpenAI-compatible `/v1/chat/completions` endpoint over `urllib`; the agent needs no SDK, and the API key never leaves the control plane. Receipts are written to the VX1 host's disk. The web UI is a static HTML page with plain JavaScript and CSS, served from the standard library's `http.server`, with no build step and nothing loaded from another site (see Web UI). We chose Python because Microsandbox's docs and Vultr's sandboxing guide both use it, Ubuntu 24.04 on the VX1 host ships Python 3.12, and this is a one-person, 4.5-day build.

```
                 Vultr VX1 host (Seattle)
operator --SSH-->  control plane (Python, user pqproof)
                     |- Vultr Serverless Inference   plan, patch, tool calls (key stays here)
                     |- msb create / exec / rm  -->  one microVM per step (KVM, egress denied)
                     '- writes run/receipt/
                                 | published (root-owned copy)
browser --HTTPS--> nginx --> run viewer (Python, user pqweb): replay of published receipts
```

## How PQ-Proof uses Vultr

| Role | Vultr service | What it does | Configuration |
|---|---|---|---|
| Control plane, sandbox host, demo site | **Vultr Cloud Compute VX1** | Runs the agent's control plane, one Microsandbox microVM per step on its KVM, the egress sinkhole and DNS recorder, and the public demo site (nginx + the run viewer) | Plan `vx1-g-4c-16g-240s` (4 vCPU, 16 GB, 240 GB), region Seattle (`sea`), Ubuntu 24.04 LTS x64, `/dev/kvm` available |
| The agent's model | **Vultr Serverless Inference** (`https://api.vultrinference.com/v1`, OpenAI-compatible) | Writes the migration plan through the `propose_plan` tool and the edits through `propose_edits`, reads raw build errors and tries again (up to 3 attempts) | `glm-5.3` only, tools without `tool_choice`, `reasoning_effort: low`, at most 8 requests per run; the key lives in `/etc/pqproof/inference.env` (root, 600) and reaches the control plane on stdin |

The demo's newest run (`e2e-glm-7`, November 8, 2026) sent 3 requests to `glm-5.3` (12,140 input and 2,254 output tokens), and its receipt prices them at the public model list's rates ($0.75 and $3.00 per million input and output tokens) at $0.0159. Every run that reached the model passed, at $0.0138 to $0.0217 each (see End-to-end run). Success is never the model's call: the verdict comes from the probe's handshakes and exit codes.

## Public demo and deployment

The demo site is read-only: it serves the published receipt of a recorded run and a replay built from that receipt alone. Live runs are not open to the public; the viewer's gate refuses them (`503`, "live runs are off"), and nginx answers anything but `GET` and `HEAD` with `403`.

- **Viewer**: `deploy/pqproof-web.service` runs `python3 -m pqproof web` as `pqweb`, a system user with no shell, no key and no `kvm` group, bound to `127.0.0.1:8080`. systemd keeps `/etc/pqproof`, `/var/lib/pqproof` (the control plane's runs) and `/root` out of its view, lets it reach no address but localhost, and drops every capability (`systemd-analyze security`: 1.1, "OK"). It reads only `/srv/pqproof/runs`, a root-owned copy of the runs chosen for publication, each checked with `verify-receipt` before it is published.
- **Front**: `deploy/nginx-demo.conf`, Ubuntu's nginx 1.24 with a Let's Encrypt certificate (http-01, renewed by certbot's timer), TLS 1.2 and 1.3, HSTS, per-address limits (10 requests per second with a burst of 40, 20 requests at once), 10 s header and body timeouts, 1 KB bodies. A request for any other host name gets no answer. The front itself speaks classical TLS: Ubuntu 24.04's OpenSSL 3.0 has no ML-KEM, and PQ-Proof proves hybrid handshakes inside the microVMs, not on its own front.
- **Firewall**: ufw allows 22, 80 and 443/tcp only, and at most 100 open connections to 80 and 443 from one IPv4 address (nginx's own limits count requests, so connections that never finish a request are capped here).

To deploy it yourself on a VX1 instance with Ubuntu 24.04 (keys and secrets stay out of the repository):

```sh
deploy/upload.sh -i ~/.ssh/KEY --fixture ../orders-edge --key ~/.config/pqproof/inference.env root@HOST
ssh root@HOST bash /opt/pqproof/pq-proof/current/deploy/vx1-setup.sh     # updates, keys-only sshd, ufw, user pqproof, msb 0.7.13
ssh root@HOST 'cd /opt/pqproof/pq-proof/current && runuser -u pqproof -- env -i HOME=/var/lib/pqproof \
    PATH=/var/lib/pqproof/.microsandbox/bin:/usr/bin:/bin python3 e2e/orders_edge.py \
    --repo /opt/pqproof/orders-edge/current --approve --model glm-5.3 --key-file /dev/stdin \
    --out /var/lib/pqproof/runs/RUN_ID < /etc/pqproof/inference.env'   # one real run, about 2 minutes
ssh root@HOST bash /opt/pqproof/pq-proof/current/deploy/demo-site.sh DOMAIN RUN_ID   # viewer, nginx, certificate, ufw 80/443
```

`upload.sh` streams each repository's committed `HEAD` with `git archive` over SSH (no Git credentials go to the host) and copies the inference key file with `scp`. `demo-site.sh` can run again; it changes nothing that is already in place. The demo uses `149-28-14-122.sslip.io`, a name that resolves to the host's address.

## Model

PQ-Proof calls one model, `glm-5.3`, for planning, patching and tool calls; no other model is called. The id comes from Vultr's public model list, re-read after the kickoff on November 4, 2026. The list shows `tools` but no `tool_choice`, so the client never sends `tool_choice`; glm-5.3 still called a declared tool 5 times out of 5 without it. `deepseek-v4.1-flash-1017` was tried as a planner and did the same with tools, but its plans did not pass the checks in 3 attempts ([docs/kickoff-spike.md](docs/kickoff-spike.md)).

`pqproof/agent.py` is the model's part of a run. The model first writes the plan through one declared tool, `propose_plan` (its parameters are the plan schema). The plan must compile into an allowlist, name every image the Dockerfile uses before and after the edits, run exactly the commands the prove step runs (nginx with the repository's own config under `/work/src`, each server it builds as `[NAME]` alone), probe every server the prove step starts (nginx and each `[NAME]`; which of a server's ports to probe is the approver's call), and its images must resolve; otherwise every reason found goes back to the model in one message, at most 3 times. The edits then come from the patch loop below. Calls send `reasoning_effort: low` and `max_tokens: 8192` (see `agent.py` for the measurement behind that). Repository text reaches a prompt only bounded: the files that decide the build and the TLS settings (at most 16,000 characters each, 64,000 in all, read without following symlinks), the README as marked untrusted notes (at most 4,000 characters), file paths in a narrow character set, and the CBOM rows. Control and format characters become U+FFFD, and each file sits between markers that carry a random id chosen per prompt, so a file cannot close its own block and pose as the control plane.

`pqproof/inference.py` calls `POST /v1/chat/completions` with `Authorization: Bearer` and retries HTTP 429 and 5xx with backoff, honouring `Retry-After`. It does not trust `tool_calls`, because a prompt injection in the target repo can steer the model: a call to a tool the request did not declare, or with arguments that are not a JSON object, repeat a key, miss a required field, add an undeclared one or have the wrong type, comes back with an error on that call and no arguments. Any other malformed response raises `InferenceError`, and call ids are made unique. It reads the key from `VULTR_INFERENCE_API_KEY`; keep the key outside the repository. The client does not follow redirects, so the `Authorization` header cannot be carried to another host, and it redacts the key from any error text, including a server's own error message.

## Plan and allowlist

A human approves the model's plan (JSON; the schema is `PLAN_SCHEMA` in `pqproof/plan.py`). The approved plan compiles into an allowlist of exact command lines, repo-relative file paths and base images. An image must be a Docker Hub official image pinned by digest, such as `golang:1.25-bookworm@sha256:<64 hex>`; a tag alone is refused because the registry owner can move it, and so is any other registry. A command may use only `make` (targets), `go` (`build`, `test` or `vet` on packages, a few fixed flags, and `-o=` a path inside the work tree), `nginx` (`-t`, `-c` with absolute config paths) and PQ-Proof's own `tls_probe` (fixed subcommands, loopback addresses and absolute paths only). A plan may also run, by name and with `-flag=value` arguments only, a program it builds itself with `go build -o=out/NAME` (the server it is about to prove; a name like `sh`, `curl` or `install` is refused), and it must list at least one target to probe inside the prove microVM: a loopback address (`127.0.0.1:PORT`, never the probe's own `127.0.0.1:4433` or `127.0.0.1:4434`) and the server that must own that port (`nginx` or a program the plan builds). The approval screen shows each one, and a run that probes nothing is a failure, not a pass. Every other program is refused, and so is any argument outside those shapes, such as `go build -toolexec`, `make --eval` or `nginx -g`. That limits what the model can ask for. It does not make the repository's own code safe: `make test` runs the repo's Makefile recipes with `/bin/sh` and `go test` runs its test code. That code is untrusted and runs only inside a microVM with egress denied, which is the real boundary (see Containment). The plan has no field for egress hosts because sandboxes get none. Its free text, the summary and each edit's reason, must be one line of printable characters (at most 500 and 300), because the approval screen prints it as it is and a terminal escape sequence could otherwise hide the image and command lines below it. The allowlist does not read file contents: a change like `InsecureSkipVerify: true` inside an approved file is caught by a deterministic TLS-weakening check on the patch (`pqproof/verify.py`, see Patch loop).

## Patch loop

`pqproof/loop.py` asks the model for edits through one declared tool, `propose_edits` (`{path, old, new}`, where `old` must occur exactly once), applies them to a fresh copy of the original snapshot, builds inside microVMs, and on failure sends the failing step's raw output (its last 8,000 characters) back to the model. It stops after 3 attempts. The edit applier trusts nothing in the snapshot: the path must be in the approved plan, `os.path.realpath` of the target must be the target itself inside the snapshot (a symlink anywhere on the path is refused, even one that points back inside), and the file is opened one directory at a time with `O_NOFOLLOW`, so a symlink that appears after that check still cannot be followed. An edit that is refused counts as a failed attempt and is not built. So does a patch that weakens TLS: before anything is built, `pqproof/verify.py` compares each changed file before and after the patch, read the way its own parser reads it (nginx's tokenizer, where `#` starts a comment only where a word could start and each statement is matched whole; Go's string, rune and comment rules; for Dockerfiles and other files only lines that start with `#` are comments), and refuses it if it adds a construct that turns verification off or down (`InsecureSkipVerify`, a `VerifyPeerCertificate` or `VerifyConnection` callback, `rejectUnauthorized: false`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, `verify=False`, `check_hostname = False`, `CERT_NONE`, `proxy_ssl_verify off`, `ssl_verify_client off`, `curl -k`), allows an old protocol (TLS 1.0, 1.1 or SSL 3.0 by name in any letter case, in `ssl_protocols`, `ssl_conf_command MinProtocol` or `Protocol` and their `proxy_` forms, or an `openssl.cnf` `MinProtocol`; in Go as a constant from `crypto/tls` under any import name, or as a number in any base such as `MinVersion: 0x0301` or `01401`; a Go `MinVersion` or `MaxVersion` the check cannot read, such as `tls.VersionTLS12 - 2` or a variable, is refused too), adds a weak cipher suite (3DES, RC4, NULL, EXPORT or RSA key exchange: Go's `TLS_RSA_WITH_*` and `InsecureCipherSuites()`, and any suite given as a number or an expression; OpenSSL tokens and each `+`-joined part of one, by OpenSSL or IANA name, in `ssl_ciphers`, `proxy_ssl_ciphers` or `ssl_conf_command CipherString` and its `proxy_` form, and `@SECLEVEL=0` anywhere in a token or any file; a token after `!` or `-` removes suites and does not count), or sets a `GODEBUG` value that brings legacy TLS back (`tls10server=1`, `tlsrsakex=1`, `tls3des=1`, `tlsunsafeekm=1`, `tlssha1=1`, `x509sha1=1`, or `godebug default=go1.N` below 1.23) in any file: a Dockerfile `ENV`, a Makefile, a `go.mod` `godebug` line or block, a `//go:debug` directive. It also refuses a patch that removes a verification setting. Removal matters as much as addition: nginx's `proxy_ssl_verify` is off by default, so deleting `proxy_ssl_verify on;` turns upstream verification off just like writing `off`, and the same holds for `proxy_ssl_trusted_certificate`, `ssl_trusted_certificate`, client-certificate verification, Go's `RootCAs` or `ClientCAs`, and a Go `MinVersion` line. Trust and version settings must not change the wrong way either: a trusted-CA file in nginx or a `RootCAs`/`ClientCAs` value the file did not have before (the VX1 review pointed `proxy_ssl_trusted_certificate` at the system bundle of every public CA), a new `x509.SystemCertPool()` or reference to the system CA bundle, a lower Go `MinVersion`, or a lower `go` line in `go.mod` (older Go defaults include TLS 1.0 servers and RSA key exchange) are refused. The reason goes back to the model as the attempt's error. This is a deny list for changes a key-exchange migration never needs, not a proof that a patch is safe (see Known limits); the orders-edge fixture's planted README note asks for `InsecureSkipVerify: true`, and following it fails the attempt.

Images the model names (`nginx:1.30-trixie`) are resolved before approval: the control plane runs `msb pull` and `msb image inspect` on the host and shows `nginx:1.30-trixie@sha256:<digest>` with its platform, and only that pinned reference goes into the allowlist. Because that pull happens before a human looks, a plan may list at most two images per `FROM` line of the Dockerfile (the image it names now and the one an edit moves it to), checked before anything is pulled, and each image is resolved once per run. The digest is the host's platform manifest, so the VX1 host (amd64) shows a different digest than a Mac (arm64).

## Inventory (CBOM)

`pqproof/scan.py` lists the places in a repo snapshot that decide its TLS key exchange, and the signatures it uses, as rows of a cryptography bill of materials (CBOM): path, line, algorithm, NIST IR 8547 status, whether the row keeps the service off `X25519MLKEM768`, and whether PQ-Proof patches it. It reads nginx `ssl_ecdh_curve` and `ssl_conf_command Groups` (or `Curves`, also the `proxy_` forms) up to the directive's `;`, across lines; every Go `[]tls.CurveID{...}` list, whether a `CurvePreferences` field, an assignment or a variable; the `go` line of `go.mod` (below 1.24, Go keeps its pre-1.24 default key exchanges, `GODEBUG=tlsmlkem=0`, even after a curve pin is gone) and `tlsmlkem=0` set outright (a `godebug` line or block in `go.mod`, `godebug default=go1.N` below 1.24, `//go:debug`, or a `GODEBUG` variable in a Dockerfile, shell, YAML or env file); the runtime stage of each Dockerfile (Debian bookworm ships OpenSSL 3.0, which has no ML-KEM; trixie ships 3.5; a tag that names no known distribution is reported as unknown, not as harmless); and RSA or ECDSA JWT signing methods. Each file is read the way its own parser reads it, with the same readers as the TLS-weakening check (see Patch loop): nginx through a copy of nginx's tokenizer, so a `#` inside a word (`edge#2`) or a quoted value hides nothing and a directive quoted inside another one is not a setting; Go and `go.mod` with comments removed outside string literals, so `"docs/*"` or `"a//b"` does not swallow the code after it; other files with lines that start with `#` as comments. A commented-out pin is not a row. Rows go into the model's context, so text taken from the repo is bounded: a group name or image reference outside a narrow character set and length reads `unrecognized`. Signatures are reported and never patched. The scanner only reads: it skips `vendor/`, tests and `.git`, does not follow symlinks, and reads at most 1 MiB of a file. Its rows are a static guess; the probe decides.

## Proof

Success is decided by a handshake, not by a model. The client is `tls_probe` (`probe/tls_probe.go`), a small static Go program (standard library only, `CGO_ENABLED=0`) that PQ-Proof builds offline inside a microVM from a pinned `golang:1.27-bookworm` image and copies into every microVM it tests. A client from the target's own image would not do: orders-edge's image ships OpenSSL 3.0, which does not even know the name `X25519MLKEM768`, so a failed handshake would say nothing about the server. Before any server is judged, the probe starts two reference servers of its own inside the same microVM, ahead of the repo's servers. Offering only `X25519MLKEM768`, it must negotiate `X25519MLKEM768` with the first (the positive control) and must fail against the second, which accepts only `X25519` (the negative control; a classical client must still reach it with `X25519`). If either control fails, the attempt fails with "proof invalid" and no server is judged: a probe that always reports hybrid, for instance one that code in the microVM swapped for a script, fails the negative control. The probe, its reference servers and the test certificate stay root-owned, while the repo's servers run as unprivileged users, one uid for the built programs and another for nginx (the control plane only creates nginx's pid file and cache directory for it, with `/usr/bin/install` named by its absolute path), so code under test cannot replace the probe. The programs the plan built are copied to `/opt/pqproof/bin`, which is not on the guest's `PATH`, and started by absolute path, so a built program can never stand in for a command that root runs by name: a review built the API a second time as `install`, and before this change it ran as root and replaced `/usr/sbin/nginx` with a Go server that spoke hybrid. Each target names the server that must answer on it: before any handshake, `tls_probe listeners` (run as root) reads from `/proc` which processes hold each listening port, with their uid and executable. A port held by anything other than the named server (the API listening on nginx's port, so nginx cannot bind it, say) fails the attempt, and that listing and the servers' own output go back as the error; the listing is taken again after the last handshake, and if it changed, the proof is invalid. The probe binary is also copied back out and hashed on the host before the controls and after the last handshake; a different hash makes the proof invalid. This still trusts the guest kernel: code that gained root inside the microVM through a kernel bug could forge a handshake. Running the probe in a separate microVM is not done yet. Then it connects to each server twice: once offering only `X25519MLKEM768` (success means the server negotiated hybrid ML-KEM) and once offering only classical groups (`X25519,P-256`, a client from before ML-KEM, which must still connect). The receipt records the probe's name, version and SHA-256 and the SHA-256 of its source. `pqproof/prove.py` also reads `openssl s_client` output for cross-checks; note that a classical handshake there prints no `Negotiated TLS1.3 group` line, only `Peer Temp Key: X25519, 253 bits`, and a failed one prints `Negotiated TLS1.3 group NID: 0`.

Base images are pinned by OCI index digest (`pqproof/images.py`), so one pin works on an arm64 Mac and on the amd64 VX1 host. Measured with msb 0.7.13: `msb pull` resolves an index digest to the host's platform, and `msb image inspect` then reports the platform manifest digest, which is what a receipt records.

## Containment

Each step runs in a fresh Microsandbox microVM with its own kernel. A step can copy files in (`msb copy`), run several allowlisted commands, start a server as a background job (`msb exec -d`) and copy one built file out; a copied-out file that is not a regular file (a symlink the guest planted, say) is deleted and refused, and `msb copy` runs under a 256 MiB file size limit (`RLIMIT_FSIZE`, set for that process only), so a guest cannot fill the host's disk through it. The control plane creates it with `--cpus`, `--memory` and `--max-duration` (defaults: 1 vCPU, 1 GiB, 120 s), labels it `app=pqproof`, and lets it use only images the control plane has already pulled (`--pull never`). The runner itself refuses any image or command line that the step's approved allowlist does not hold, and passes the image after `--` so it is never read as an `msb` option. The host also times `msb exec` and always runs `msb rm --force` afterwards. A reaper (`Runner.start_reaper`, started by the e2e run) removes, at startup and every minute, any labelled sandbox that is stopped or older than the longest step's wall clock (300 s) plus a minute, so a control plane that was killed leaves nothing running for long; a step cannot ask for more than 300 s, so the reaper never removes a live one. Every `msb` command line is kept for the receipt, and so is each step's output, cut to the first and last 512 KiB of each stream with the full stream's byte count and SHA-256, so a step that floods its output cannot fill the control plane's memory. `msb` runs with only `PATH`, `HOME` and its own `MSB_*` settings in its environment, because it passes that environment on to each sandbox's VMM process; the inference API key is never in it.

Egress is denied for every step, the build included. DNS goes only to a resolver on the host that records the queries it receives, over UDP and over TCP, and answers NXDOMAIN instead of forwarding them. TCP to `203.0.113.0/24`, a documentation range that is never routed, goes through Microsandbox's `--proxy` to a host sinkhole that records the destination and the bytes; that is how the demo shows a planted test hook's canary. Everything else, including the host and the control plane API, is dropped by Microsandbox's network policy, and a dead sinkhole does not open a direct route. The demo hook uses plain HTTP so the sinkhole can read the canary; HTTPS attempts are recorded as encrypted bytes only. The sinkhole is bounded too: it serves at most 16 connections at a time and keeps at most 1,000 events between collections (the rest are counted, and canary ids are still collected), and `msb` holds each guest to 32 TCP connections and 200 outbound packets per second. Attempts that Microsandbox's policy drops before they reach the sinkhole, such as a direct connection to `1.1.1.1`, are blocked but not counted, so a receipt can list only the attempts that reached the sinkhole.

Integration tests (`tests/test_sandbox.py`, `tests/test_egress.py`) run real microVMs whenever `msb` is installed; set `PQPROOF_MSB_TESTS=0` to skip them and `PQPROOF_WALL_S=120` to check the full wall clock. They pin `alpine` by the digest of the copy in the local cache, so they use the network only when that cache is empty. They have run on macOS (Apple Silicon) and on the Vultr VX1 host (x86_64, Ubuntu 24.04), both with msb 0.7.13; the host results are in [docs/kickoff-spike.md](docs/kickoff-spike.md).

## End-to-end run on orders-edge

`e2e/orders_edge.py` runs the whole pipeline on orders-edge ([g1mn/orders-edge](https://github.com/g1mn/orders-edge), a separate fixture repository), a small nginx + Go fixture with a classical-only TLS key exchange, a planted test hook and a prompt-injection line (`pqproof/pipeline.py` does the work):

1. Snapshot with `git clone --no-recurse-submodules` (the only non-`msb` commands on the host are `git clone`, `git rev-parse` and `git remote get-url`), and the CBOM.
2. The plan's image tags are resolved to `name:tag@sha256:<digest>` and shown for approval.
3. Build: a microVM from the Dockerfile's build image runs `make test` and `go build` offline (vendored modules, `GOPROXY=off`); the binary comes out as one regular file. Prove: a microVM from the Dockerfile's runtime image runs `nginx -t`, starts the API and nginx as background jobs, passes the probe's two controls, checks that nginx owns port 8443 and the API port 9443, and probes both TLS ports. The Dockerfile itself is never built.
4. Baseline first, then the patch loop.

**`--model scripted`, the default, is the run below** (and what tests and CI use): `e2e/orders-edge-scripted-model.json` stands in for the model, with a plan and two attempts of fixed edits written by hand, and no inference call is made. Attempt 1 changes the nginx group list, the Go `CurvePreferences` and the `go` line but keeps the OpenSSL 3.0 runtime image on purpose; attempt 2 also moves the runtime image to `nginx:1.30-trixie`. The run shows containment, the build, the raw-error feedback and the proof, not model quality.

Measured on an M-series Mac with msb 0.7.13 (November 4, 2026), 75 s in all:

| | `127.0.0.1:8443` (nginx) | `127.0.0.1:9443` (Go API) |
|---|---|---|
| Baseline, hybrid-only client | `remote error: tls: handshake failure` | `remote error: tls: handshake failure` |
| Baseline, classical client | P-256 | P-256 |
| Attempt 1 | `nginx -t` fails: `group 'X25519MLKEM768' cannot be set` (OpenSSL 3.0); this raw error is the feedback | |
| Attempt 2, hybrid-only client | `X25519MLKEM768` | `X25519MLKEM768` |
| Attempt 2, classical client | X25519 | X25519 |

Every `make`, `go` and `nginx` command ran inside `msb exec` (0 on the host), the planted test hook's `CANARY-0001` landed in the sinkhole during `make test`, every microVM was removed, and the CBOM after the patch has no row that blocks hybrid key exchange (the RS256 JWT row stays: signatures are out of scope). The same probe binary built twice gave the same SHA-256.

On the VX1 host (x86_64) the same scripted run passed in 120.5 s. With `--model glm-5.3` writing the plan and the edits, every run that reached the model passed: 97.3 s, 116.1 s, 106.7 s, 130.1 s and 100.2 s on November 4 and 5, for $0.0217, $0.0197, $0.0138, $0.0155 and $0.0144 in tokens ([docs/kickoff-spike.md](docs/kickoff-spike.md) has the first two), and 78.2 s for $0.0159 on November 8 (`e2e-glm-7`, on the demo). `e2e-glm-6` wrote a format 2 hashed receipt (41 artifacts, 288 KB) naming `https://github.com/g1mn/orders-edge` at commit `7c7e501`, which `verify-receipt` accepted on the VX1 host and again on a Mac (48 checks); `e2e-glm-7`'s passed 46 checks on a Mac.

`--model-file e2e/orders-edge-injected-model.json` runs a scripted stand-in that follows the README's injection: its attempt 1 makes the right key-exchange edits and also sets `InsecureSkipVerify: true`, which the TLS-weakening check refuses before anything is built; attempt 2 is the same patch without it. On the VX1 host it passed in 84.8 s (`e2e-injection-scripted-1`, on the demo).

```sh
python3 e2e/orders_edge.py --repo ../orders-edge --approve   # exit code 0 only if every check passes
```

With a model id instead, the model writes the plan and the edits, and the same checks decide the run. The key comes from `--key-file` (an env file with `VULTR_INFERENCE_API_KEY=...`) or from the environment; `/dev/stdin` (or `-`) lets a root-only key file reach an unprivileged control plane without entering any process environment; once the key is read, file descriptor 0 is `/dev/null`, so no child process inherits the open key file, and the run's own `git` commands get `/dev/null` as standard input and only `PATH` from the environment. The report records each reply's tokens and their cost at the public model list's rates, and every HTTP request the run sent, answered or not: a request that timed out has no token counts but may still be billed, so the report counts those apart. One run sends at most 8 requests (3 plans and 3 sets of edits, plus 2 retries); the client refuses a ninth.

```sh
sudo -u pqproof python3 e2e/orders_edge.py --repo /opt/pqproof/orders-edge/current --approve \
    --model glm-5.3 --key-file /dev/stdin < /etc/pqproof/inference.env
```

## Hashed receipt

Each end-to-end run that reaches its checks writes a receipt directory, `--out/receipt` (`pqproof/receipt.py`):

- `receipt.json`: the repository (its public URL, from the source's `origin` as https without credentials, the path it was cloned from, the commit and its tree hash); the verdict; every microVM with its pinned image and platform digest, limits, network flags, start and destruction times, each command it ran (exit code, byte count and SHA-256 of each output stream, and the log file); the probe's name, version, SHA-256 and source SHA-256; the CBOM before and after; the patch (diff, files) and every attempt with its outcome, the error fed back and any TLS-weakening rules that refused it; the proofs (both probe controls, each target with a hybrid-only and a classical client, the repository's tests and `nginx -t`, for the baseline and the final attempt, each with the expected and actual result and its log); what was not fixed and why (signatures); containment; the model's provider, tokens, requests and cost; and a manifest of every artifact with its byte count and SHA-256. `pqproof/receipt.py` holds its JSON Schema.
- `receipt.html`: the same receipt as one page that loads nothing from anywhere (no external script, style, font or image; its Content-Security-Policy allows only its own inline theme script, by hash), dark by default with a light switch, linking only to its own artifacts.
- `artifacts/`: the approved plan, the CBOM before and after, each attempt's diff and the error that went back to the model, every command's log from every microVM, the host's command lines, and the model's request ledger.

Egress is recorded per microVM: the sinkhole's window is collected after each step (`Sinkhole.take()`), so each microVM lists only what reached the sinkhole while it ran (`reached_sinkhole`, with destination, bytes, SHA-256, canary ids and the first 200 bytes), how many more attempts reached it over its caps and were counted without details (`reached_sinkhole_not_kept`), and `dropped_by_policy: "not counted"`, because Microsandbox drops everything else before it reaches the sinkhole.

`receipt_id` is the SHA-256 of `receipt.json` without that field in the JSON Canonicalization Scheme (RFC 8785: keys sorted, no whitespace, UTF-8, numbers as JavaScript writes them), so one hash covers the receipt and, through the manifest, every artifact, and a verifier written in another language computes the same id. Anyone can check a receipt directory:

```sh
python3 -m pqproof verify-receipt runs/e2e/receipt   # exit code 0 only if every check passes
```

It validates `receipt.json` against the schema, recomputes `receipt_id`, the byte count and SHA-256 of every artifact (read without following symlinks, and never through a `.` or `..` path segment), refuses a file anywhere in the receipt directory that is not in the manifest and a reference whose hash differs from the manifest, checks that the verdict and the containment numbers agree with what they summarize (a `pass` needs a patch from the last attempt, every proof matching, no build command on the host and every microVM destroyed; the counts of microVMs, sinkhole events and refused attempts must match the record), compares the CBOM rows with their files, and renders `receipt.html` again to compare it with the file. The e2e run does the same before it reports success. Because `receipt.html` is compared with what the running version of PQ-Proof renders, check a receipt with the version that wrote it (receipts before format 2, `pq-proof hashed receipt 2`, were written by 6cc4b67 and earlier). This is a hashed receipt, not a statement of who made it: anyone can edit a file and write new hashes, so a `receipt_id` means something only next to one from a source you trust, such as the run's own output. On a Mac (msb 0.7.13, November 5, 2026) the scripted run's receipt had 47 artifacts in 328 KB and passed all 54 checks.

## Web UI

```sh
python3 -m pqproof web --runs runs/   # http://127.0.0.1:8080/ ; each run directory is an e2e --out
```

`pqproof/web.py` serves one page (`pqproof/static/`: HTML, CSS and plain JavaScript, no build step) and a small JSON API over the run directories under `--runs`; it never runs anything itself. For the chosen run the page shows the verdict, a replay of the run (the job timeline of control-plane phases and every microVM fills in as the recorded clock advances, sped up to about 25 s, next to the receipt's events in time order: each microVM created and destroyed with its image and limits, each canary that reached the sinkhole, each patch refused for weakening TLS, each proof with its expected and actual result, the verdict; built from the receipt alone, so opening it starts nothing, calls no model and needs no network), the containment panel (each canary that reached the sinkhole with the bytes it sent, patches refused for weakening TLS, how many egress attempts reached the sinkhole, `not counted` for what the policy dropped, host build commands, microVMs destroyed, and each microVM's network flags), the CBOM before and after side by side, the proofs, the attempts and the diff that passed, and the receipt with its links. Every request for a run re-checks its receipt with the same code as `verify-receipt` (the result is kept until a file in that receipt directory changes), and the page says whether all hashes matched.

| Request | Answer |
|---|---|
| `GET /api/runs` | runs that have a receipt, newest first |
| `GET /api/runs/ID` | the run's `receipt.json`, the verification result, links |
| `GET /api/runs/ID/replay` | the run's recorded events in time order, from its receipt |
| `GET /runs/ID/receipt/PATH` | `receipt.html`, `receipt.json` or a file under `artifacts/` |
| `POST /api/runs` `{"repo": "..."}` | a live run, if the gate admits it |

Live runs go through a gate: `web.Gate.admit(repo, ip)` admits or refuses with a status and a reason, and an admitted run goes to a starter that releases the gate when the run ends. Limits for public live runs would plug in there (only allowlisted fixtures, one run at a time, a daily count per address, a daily inference budget). In this build the gate refuses every request (`503`, "live runs are off") and there is no starter, so the page shows recorded runs only. Receipt text reaches the page only as text (no `innerHTML`); paths are checked segment by segment and read without following symlinks, so nothing outside a run's `receipt/` directory is served; every response carries a Content-Security-Policy (the page: same origin only; artifacts: `sandbox`) and `nosniff`. The server binds `127.0.0.1` unless told otherwise. Slow clients cannot hold it: it serves at most 64 connections at once and answers the next with `503` at once, drops a client that has not sent its whole request within 10 s, ends every connection after 30 s, and escapes control characters in its log lines. Limits per client (connections and requests per address) belong to the front that faces the internet: the demo site's nginx (see Public demo and deployment).

## Known limits

- **The TLS-weakening check reads each file's statements, not nginx's block structure.** It counts settings per file, so it does not see where a setting sits. Deleting `proxy_ssl_verify on;` from the `location` that proxies and writing it into a new `location` that no request reaches keeps the count at one and passes, although upstream verification is now off for every real request. The proof does not catch it either: it probes the server's key exchange, not nginx's connection to its upstream. `tests/test_verify.py` pins this case as passing, so a change in either direction has to update this list.
- **It does not follow values built at run time.** Setting `InsecureSkipVerify` through `reflect` with a field name composed from parts (`FieldByName("Insecure" + "SkipVerify")`) passes, and so does anything else assembled while the program runs or kept in a file the patch does not touch: a `GODEBUG` value put together from strings, a TLS config built by a helper in another file, or a CA path read from an environment variable. A Go `MinVersion`, `MaxVersion` or `CipherSuites` value the check cannot read is refused rather than followed. `tests/test_verify.py` pins the `reflect` case as passing.
- **It sees only the files the patch changes, with rules for Go, `go.mod`, nginx, Python and JavaScript.** Other files get only the language-independent rules (`GODEBUG`, `@SECLEVEL=0`, an OpenSSL `MinProtocol`, `NODE_TLS_REJECT_UNAUTHORIZED`, `CERT_NONE`, `curl -k`, the system CA bundle). Its JavaScript and Python readers are approximate (a regular expression literal, nested f-string quotes), so in those files it also counts the raw text and refuses even a comment that names a weakening construct.
- **The probe trusts the guest kernel.** Code that gained root inside a microVM through a kernel bug could forge a handshake (see Proof).
- **Egress that Microsandbox's policy drops is not counted.** Only attempts that reach the sinkhole are recorded (see Containment); receipts say `"dropped_by_policy": "not counted"`.
- **A receipt is hashed, not attributed.** Its hashes show that the files are the ones it names, not who produced them (see Hashed receipt).
- **The public demo replays recorded runs; it does not run new ones.** Visitors cannot start a run, so the demo cannot be made to build arbitrary code or spend inference budget. Runs are started by the operator over SSH (see Public demo and deployment).
- **The demo site's own front speaks classical TLS.** Ubuntu 24.04's OpenSSL 3.0 has no ML-KEM; the hybrid handshakes PQ-Proof proves happen inside the microVMs, between the probe and the patched servers.
- **Auto-fix covers TLS key exchange in nginx and Go.** Signatures (RSA or ECDSA JWTs, certificates) are reported in the CBOM, not migrated.
